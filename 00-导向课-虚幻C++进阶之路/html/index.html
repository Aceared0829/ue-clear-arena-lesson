为什么用「境界」这种叫法

因为它天生带三件事：可以并级、可以跳、没有官方认证。比「初级/中级/高级」诚实得多——那套分级总让人误以为在排队。

时间量级怎么看

按全职投入估算，不是承诺，也不是门槛。带项目、有人带、只做一个模块，都能大幅压缩；反过来，一年只碰两次引擎，就别按这个表算。

先给整段路，再逐级展开。三条常被误解的点：① 这是能力刻度不是职级；② 大多数人一辈子停在筑基、金丹，很正常；③ 借用修仙的壳是为了好记——炼气是入门，化神是传说，中间三段才是常态。时间量级只是参考，别当成承诺。下面那排卡片不用逐条念，讲清「每一级都有一个典型产出」就够了。

急着写 C++ 没错 —— 但请带着这四个问题写
① 它在谁手里活着谁创建、谁持有、谁在什么时机销毁？GC 凭什么不回收它
② 它该写在哪一层Actor / UObject / 组件 / 函数库——选错层，代码就散
③ 它为什么这么写宏、模块、反射不是语法糖，是引擎的规矩，问一次为什么

提前学 C++ 完全可行，引擎源码就是最好的教材。但「先写通再补原理」的账，早晚要还——差别只是现在想，还是三个月后返工。

这一页的态度要讲明：炼气期直接写 C++ 完全可以，甚至鼓励——引擎源码就是最好的教材，早动手早开窍。真正要拦住的不是「写」，而是「只写不想」。这四个问题是提前写 C++ 的人必须先挂在墙上的：谁持有它、写在哪一层、为什么这么写、换个人能不能改。今天不要求答对，但要求每写一段都问一次。

为什么会有这么多差异

UE4 是 2014 年的设计，UE5 在 2020 年后逐步替换。Epic 保留了向后兼容，所以旧代码还能编，但新项目不该照着写。

同类替换（认识名字即可）

StateTree 部分替代行为树 · MetaSounds 替代 Sound Cue · Chaos 替代 PhysX · World Partition 替代 Level Streaming

见到旧教程怎么办

先认版本：看发布日期、看有没有 Enhanced Input、看有没有 TObjectPtr。三样都没有，就是 4.x 的。

看到旧教程不用慌，先认出它用的是哪套。

这页是给学生「解雷」的。课上一律按 5.8 讲，但不假装旧写法不存在——旧项目里到处都是，能认出来比骂它有用。判断版本的三招（发布日期 / Enhanced Input / TObjectPtr）是这页最实用的东西。

虚幻 C++ ≠ C++

C++ 只是地基，剩下五块是「引擎的规矩」。很多人学不下去，是只学了第一块。

01 · 基础标准 C++

语法、指针、类、模板、RAII——唯一能在书上学的部分

02 · 约定引擎的 C++ 框架

Actor / Component / Gameplay 的写法约定，命名与生命周期

03 · 构建模块与插件（UBT）

代码怎么被组织、被编译、被链接到目标平台

04 · 生成反射与代码生成（UHT）

宏为什么不是注释，generated.h 里到底是什么

05 · 日常Core 的库

FString / TArray / TMap / UE_LOG / 智能指针 / 委托

06 · 桥梁与蓝图交互

UPROPERTY / UFUNCTION / 函数库 / 反射调用

六块与常见报错的对应关系——报错就是线索
unresolved external / undefined symbol→ 第 3 块（模块依赖没连上）
xxx is not a member of ...→ 第 3 块（头文件没包含或模块没公开）
Missing generated.h / UHT error→ 第 4 块（反射标记写错）
object becomes nullptr after a while→ 第 5 块（GC 参考文献没标 UPROPERTY）
blueprint can't find variable→ 第 6 块（缺 UPROPERTY 或 BlueprintReadWrite）

UE5 这些年加的 Subsystem、Enhanced Input、StateTree，不是第七块，是这六块在应用层的新补丁。

关键一句：C++ 只是地基，剩下五块是引擎的规矩。很多人学到一半放弃，不是因为 C++ 难，是因为只学了第一块，剩下的靠猜。这张「报错 → 第几块」的表是最实用的，学生遇到错能自己对号。

链接错误undefined symbol / LNK2019 → 改 Build.cs，加模块名
运行崩溃访问空对象 / 数组越界 / GC 提前回收 → 断点 + 调用栈
这四条比任何考试都准。特别是第一条——很多人以为是「我 C++ 不行」，其实是模块没加、头文件没包含。三类错误的区分是这页的核心。
What · 拆门槛

它不是什么

× 误区一

不是「背完 C++ 语法」

语法书看完也写不出一行引擎代码。引擎要的是「知道写在哪」。

× 误区二

不是「以后只写 C++」

蓝图仍然是最好的表现层工具。真正的目标是「两个都会用」。

× 误区三

不是「记住几千个 API」

记不住很正常，找得到就行。编辑器补全比十年前好太多。

真实的门槛顺序（很多人搞反了）
以为的顺序学语法 → 背 API → 才能写代码 → 才能做项目
实际的顺序看懂一个功能 → 照着改 → 改了有效果 → 知道为什么 → 能自己设计
卡住的人停在「学语法」，因为看不到语法跟项目的联系
走通的人从「改一个数值」开始，先有反馈，再要原理

门槛不在记忆量，在于知不知道该写在哪。

提前拆掉心里的门槛。学生最常问「要背多少 API」，答案是零。真实的学习顺序是反过来的：先改、再有反馈、再要原理。
Why · 引擎侧

为什么引擎要开放 C++

理由具体是什么
性能原话说了三遍——直接编译成机器码，没有解释层
可优化能优化到自己真正想优化的那一行，而不是等别人开放接口
强类型大项目里重构不容易崩，编译器帮你查一半错
开放性可定制、可扩展、可替换——从渲染到构建
迭代快不用等接口层补齐，团队自己就能往下做
生态第三方中间件几乎都是 C/C++，接得进来

它还相信开发者。

进了这个自由区，就得自己负责。给你一把能直接动刀的工具，代价是你要懂刀在干什么。

对比：如果引擎不开放 C++

所有定制都要等官方排期 → 项目被卡的永远是同一类需求 → 引擎只能服务「最大公约数」的项目。

代价是什么

学习曲线、版本升级成本、团队能力门槛。这三条，就是这门课存在的理由。

别只讲性能：真正的原因是引擎不可能替所有项目做完决定。它给你一把可以直接动刀的工具，代价是你要懂刀在干什么。生态这一条别漏——接第三方 SDK 时你就明白为什么非得是 C++。

Why · 边界

蓝图正在失去什么

说句不客气的话：AI 时代下，蓝图的作用在变小。它没死，但它的护城河只剩一条。

硬伤 01 · 版本管理二进制资产，合并不了

蓝图是 .uasset，本质是二进制。两个人改同一个蓝图，只能靠「你先提交我后改」，或者干脆分文件。代码能 merge、能 diff、能 review，蓝图不行。

硬伤 02 · 性能虚拟机解释执行

蓝图跑在 VM 上，逐节点解释。同一个逻辑，C++ 常常快一个数量级。热点逻辑放蓝图，是项目后期最常见的性能债。

硬伤 03 · AI 时代AI 写不动节点图

AI 最擅长的是文本：C++、Python、Lua、C#。对着二进制节点图，它既读不懂也改不了——这一步直接把蓝图挡在了 AI 工作流外面。

蓝图现在的唯一不可替代项
编辑器生态美术、TA、策划、音频——不写代码的人，只能在这里干活
材质、动画、Niagara、UMG 可视化预览，都是它的延伸
如果没有这套生态蓝图早被脚本语言取代了 —— 这就是为什么 Epic 还要死守它
它依然值得学因为「让非程序也能改」，这件事暂时没有第二个解
一句话概括蓝图的处境

它不是被 C++ 打败的，是被「版本控制 + 性能 + AI」三件事同时挤压。

对程序：蓝图从「主力」退成「胶水与调参层」
对非程序：蓝图仍是唯一入口，短期不会变
对你的选择：会蓝图不亏，但别把它当终点

真正的问题不是「用不用蓝图」，是你还有没有别的选项。

这页要有态度，但别变成踩蓝图。三条硬伤按顺序讲：版本管理（最痛，团队越大越痛）→ 性能（最常见的技术债）→ AI（最新的一条，也是最致命的长期趋势）。落点讲清：蓝图不会被淘汰，因为编辑器生态还在；但它的定位已经从「主战场」退到「非程序入口 + 调参层」。程序如果只会蓝图，就等于只会一个正在收缩的战场。
Why · 分工

配比早就不是 80 / 20 了

过去流行的「20% C++ / 80% 蓝图」已经不够用了。现在的常见做法是三层：C++ 内核 · 脚本玩法 · 蓝图调参。

结论

这次要学的不是「C++ 抢蓝图的活」，而是学会选层：写在哪一层，比用什么语言更重要。

为什么脚本能顶掉一大块蓝图
版本控制：文本 diff / merge / review，团队协作不再靠喊
AI 协作：AI 能读、能改、能补测试，整条流水线跑得通
热更新：不进引擎也能改玩法，运营活动不用等版本
但脚本不是万灵药
接入成本高：要自己搭绑定层，UE 官方没有「开箱即用」的脚本方案
调试体验差：断点、profiler、蓝图那种可视化都没有现成的
团队门槛：非程序直接劝退，策划还是得回蓝图

所以本课的重点不是「别用蓝图」，而是：先掌握 C++ 这一层，再判断你的项目要不要插脚本。

这页要讲清为什么 80/20 过时了。那个比例是 UE4 时代的经验值，那时没有 AI、团队也没那么在意合并冲突。现在很多项目在中间插一层脚本（Lua / Python / C# / Verse），动机就三个：版本控制、AI 协作、热更新。但别把它讲成银弹——脚本的接入成本、调试体验、团队门槛都要付代价。落点：先会 C++，再谈选层。

什么算「蓝图学明白了」

工具组合能组合引擎给的辅助工具：接口、事件分发、组件到处 Cast

依赖怎么连：三组属性

Build.cs 里的 ModuleRules，三组属性管三件事。

PUBLICPublicDependencyModuleNames

我这个模块对外暴露的头文件里用到的依赖。会传染给依赖我的模块

常见依赖写法（照着抄就行）
  PublicDependencyModuleNames.AddRange(new string[] {
      "Core", "CoreUObject", "Engine", "InputCore" });

  PrivateDependencyModuleNames.AddRange(new string[] { "UMG", "Slate", "SlateCore" });

  // 用到 AI 感知
  PrivateDependencyModuleNames.Add("AIModule");

  // 用到 Enhanced Input
  PublicDependencyModuleNames.Add("EnhancedInput");
口诀

真实报错：undefined symbol 十有八九是少加了一个模块名。这个错新手会被卡好几天

读所有带 .generated.h 的头文件（不编译，只解析）

这页可以录个屏，展示 generated.h 生成前后。三条硬规则讲完，学生 90% 的 UHT 报错都能自己解决。MYGAME_API 这条单独强调——它是最迷惑人的一类错误。

GC · 谁能被回收

UE 没有 new / delete，对象由 GC 管。规则只有一条，但违反它的代价极高。

引用链：从根出发可达的都活着
  Root Set（引擎自己抓着的：GEngine、GameInstance、Actor 等）
     │
     ├──→ 对象 A
     │       ├──→ 成员 X（标了 UPROPERTY）  ✓ 被扫描，活着
     │       └──→ 成员 Y（裸指针）          ✗ 不被扫描，可能被回收
     │
     └──→ 对象 B  ← 没有引用链到这里 → 回收

只有 UPROPERTY 标记的引用，才进 GC 分析。

非 UObject 结构体与 UObject 混用，要小心 FGCObject::AddReferencedObjects。

写法UE5 推荐
成员指针TObjectPtr<AActor> 而不是 AActor*（增量 GC 下才安全）
判空IsValid(Ptr) 而不是 Ptr != nullptr
弱引用TWeakObjectPtr<T> 不参与 GC 引用，用前判空
非 UObject用 TSharedPtr / TUniquePtr，它们不走 GC
手动标记AddToRoot() / RemoveFromRoot()，慎用
经典事故现场
  AActor* CachedTarget;          // 没标 UPROPERTY
  CachedTarget = GetTarget();
  // ... 几秒后 ...
  CachedTarget->DoSomething();      // 崩溃：对象已被回收

  UPROPERTY() TObjectPtr<AActor> CachedTarget;  // 正确

自从用了 UE，就再也不用 new / delete 了——但要记得告诉 GC「我还用它」。

最常踩的坑：裸指针存对象，看着好好的，某天突然变空。原因就是没标 UPROPERTY，GC 当它不存在。IsValid 和 TObjectPtr 这两条是 UE5 的硬要求，别用旧写法糊弄过去。

CDO · Class Default Object

在哪GetClass()->GetDefaultObject<AMyActor>()
作用蓝图里看到的默认值就是它；新对象以它为模板复制

        │
        ├── 关卡里放一个  →  复制 CDO  → 实例 A（Health = 100）

Q为什么我改了 C++ 默认值，新生成的对象就变了？

在最小场景里改一改，验证自己的理解对不对。这是唯一的验证方式。

STEP 03总结

把规律写成自己的话：什么情况用什么、为什么。写下来才算真懂。

STEP 04积累

变成资产：测试工程、函数库、笔记、图。下次直接用。

一圈的周期

一个小功能 = 一圈，几小时到几天。别指望一圈就进化一级，但也别做半圈就换方向。

第二遍做同类功能时，你不需要再查资料——这就是转完一圈的标志。

为什么叫闭环

因为积累会变成下一次模仿的素材，起点比上一次高。这是复利，不是重复。

这页是全课落点。强调「总结」这一步最容易被跳过——不写下来，下个月就忘了；写下来就变成自己的资产。四步断在哪那张图，学生看了会点头，因为大部分人都断在总结和积累。

觉悟 · 边界

什么时候动引擎

关键词是「可维护」：改引擎的代价不在今天，在下次升级。

从「不动」到「动」的四级台阶，逐级往下走
  第 0 级  不改引擎：用现有 API / 组件 / 蓝图做出来
     │        代价：0        适用：90% 的需求
     ▼
  第 1 级  插件 / 子类 / 接口：扩展而不修改
     │        代价：低       适用：想要新行为
     ▼
  第 2 级  Editor Utility / 反射：绕开私有成员，别改可见性
     │        代价：中       适用：需要访问内部数据
     ▼
  第 3 级  直接改引擎源码：包在宏或注释标记里，方便 merge
               代价：高       适用：真的没别的路
为什么能不改就不改

下次升引擎版本时，你的改动要重放一遍。改得越深、越散，重放越疼。有人在 4.27 改的东西，到 5.0 花了三周才合回去。

真要改，怎么改

统一加一段标记注释（带项目名与日期），所有改动集中搜得到；能包在宏里就包在宏里；别改签名、只加接口。

改了 C++ 基类名，蓝图找不到父类 —— 用 CoreRedirects 修（Engine.ini 里配映射）
没有基类的蓝图可以 reparent，但先备份——reparent 不可逆
讲代价：改引擎本身不难，难的是下次升版本时怎么合回去。所以要么不改，要么改得让人一眼能找出来。四级台阶这张图很实用——大部分需求都在第 0、1 级就解决了，真正需要改源码的极少。

AI 时代的这条路

AI 已经能写大部分样板：宏、BeginPlay、组件挂载、委托绑定、基础用法示例。那还学吗？

AI 能替你做的
写样板代码：UCLASS 骨架、组件挂载、输入绑定
解释报错：贴一条错误，它能给出三个方向
翻译写法：把 UE4 写法改成 UE5 写法
查 API：这个类有没有那个函数
AI 替不掉的三件事
判断这段逻辑该放哪一层 —— 它不知道你的项目结构与团队分工
判断生成的代码能不能信 —— 它不知道你的版本、你的模块、你的约束
出了问题知道去哪找 —— 它没跑过你的项目，也不知道该在哪打断点
门槛的位置变了 —— 这也是蓝图被挤下去的原因
过去门槛在「写」 ── 会不会敲这段代码
现在门槛在「判断」 ── 知不知道该写什么、写在哪、能不能信
注意AI 能读写文本：C++、脚本、配置 —— 这正好是蓝图的短板
所以「AI + 文本代码」的组合，会持续挤掉蓝图的地盘
蓝图剩下的地盘，是 AI 进不去的编辑器生态
所以六块要点、境界阶梯、源码方法论，一个都没白讲
—— 它们正好是判断力的来源，也是你「选层」的依据

AI 降低了敲代码的门槛，抬高了做判断的门槛。

这是这场课的现实意义。学生一定会问「AI 都能写了还学吗」，答案是：AI 替你打字，但没人替你决定写在哪。这三件事，AI 目前都做不了。别把这页讲成「AI 威胁论」，讲成「门槛移位」。
源码 · 入口

一切从 GEngine 开始

引擎的所有静态入口都在几个全局对象上。认识它们，你就有了「从哪开始摸」的起点。

UEngine* GEngine
是哪个类游戏用 UGameEngine，编辑器用 UEditorEngine
能拿到World 列表、游戏视口、Engine 配置
常用GEngine->GetWorldContexts() / GEngine->AddOnScreenDebugMessage()
UEditorEngine* GEditor
只在编辑器打包后的游戏里没有这个符号
能拿到当前选中了哪些 Actor / 组件、当前视口、编辑器模式
常用GEditor->GetSelectedActors() / GEditor->GetActiveViewport()
全局入口一览（认识名字，比背 API 有用）
GEngine引擎实例：World 列表、视口、调试绘制
GEditor编辑器实例：选中、视口、模式（仅编辑器）
GWorld当前 World（多数情况用 GetWorld() 更安全）
GFrameNumber当前帧号（原来是 GFrameCounter）
GLog日志系统，UE_LOG 背后就是它
GConfigini 读写，GConfig->GetString(...)
GIsEditor/ WITH_EDITOR 编译期判断
GEngineLoop主循环，Init / Tick / Exit
为什么这些入口重要

因为调试时你不知道从哪下手，第一件事就是「从全局对象往下摸」。它们是引擎这张图的几个抓手。

注意

别在构造函数里用 GetWorld()；别在 Shipping 包里用 GEditor——它不存在，会编译不过。

编辑器也是个游戏，只是一堆 UObject。

这页最容易被记住，也最容易被神化。别讲成「掌握了 GEngine 就掌握了引擎」，它只是一个入口。GEditor 只在编辑器存在这条要强调——很多人写了 GEditor 打包才炸。
源码 · 方法论

源码怎么剖析：两套视角

时空观 —— 拆开一个函数
时调用顺序与触发时机：谁先谁后、什么条件下发生、一帧里跑几次
空数据怎么流动与变形：进去什么、出来什么、中间被谁改过
用时空观看一个 Tick
时第 N 帧 → World Tick → Actor Tick → 你的 Tick
空DeltaSeconds（时间） · 你读了哪些成员（空间）
你改了哪些状态（副作用） · 谁依赖这些状态
信息论 —— 判断设计好坏
依赖越少越稳一个类知道的越少，改它的风险越小
信息就是能量传递、转换、拷贝都要消耗；能不算就不算
耦合是熵不加约束，系统自然走向混乱
七个问题，走一遍任意函数
1一开始有什么？（输入、前置状态）
2谁点的第一把火？（入口 / 触发者）
3自循环靠什么推？（Tick / 事件 / 计时器）
4外部输入有哪些？（玩家、网络、配置）
5吐出了什么？（返回值、副作用、事件）
6最后剩下什么？（持久状态）
7如果我删掉它，谁会坏？

别讲成哲学课，举一个具体函数走一遍。

别讲成哲学课，举一个具体函数走一遍。比如 Tick 的一次调用：从哪来、传了什么、改了什么、最后去哪。七个问题里第 7 个最有用——问「删掉它会坏什么」，就能看出耦合有多深。

搬：怎么借得干净

「借用」的目标是可维护，不是能跑。

四条原则
能调就不拷能直接调用 API 就别复制实现——拷过来就等于接手维护
先看输入输出搞清它依赖什么、产出什么，再决定能不能借
找那个「旋钮」想在流程里插一脚，去找 Delegate、虚函数、可重载点
别跨层调Runtime 下别去调 Editor 代码，打不包
四种「借」的代价
方式代价什么时候用
直接调用最低接口正好够用
子类重写低想在某个点改行为
复制代码中只想抄思路，不想带依赖
改引擎源码最高真的没别的路
「找不到旋钮」时的排查顺序
1这个类有没有 virtual 函数可以重写？
2有没有 Delegate 可以绑定？（OnXxx 命名多半是）
3有没有 Component 可以替换，而不用改主体？
4有没有 接口 可以实现？
5有没有 Subsystem 可以扩展？
6都没有 → 才考虑改引擎，并按前面讲的方式标记
经验引擎的扩展点比你想的多得多。找不到，通常是没找全

能跑只是及格，能维护才算学会。

很多人拷一段源码过来，跑起来了，三个月后自己都看不懂。借的标准是：半年后还能改得动。五个排查顺序很实用——大部分人卡在第 1 步就不往下找了。

为什么是这五件（每件对应一个坑）
01对应「只会用不改」 → 读懂自己项目的代码
02对应「不会挂组件」 → 掌握最基本的结构
03对应「照着旧教程写输入」 → 换上 5.x 的写法
04对应「遇到链接错误就懵」 → 亲手制造一次，以后不会怕
05对应「脑子里没有结构」 → 把隐性的理解画出来

② ③ 是 5.x 现在必须会的两条，替代「照着 UE4 教程抄一遍」。五件总共不到 7 小时，分布在 30 天里做。

这五件事分布在 30 天里做，一天十几分钟就够。给验收标准很重要：学生需要知道「做到什么程度算做完」。第 4 件看着奇怪，但它是投入产出比最高的——亲手制造一次错误，比看十次报错文档有用。
