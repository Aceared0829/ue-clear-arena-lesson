开始写 C++ 时，先考虑这四个问题
① 它在谁手里活着谁创建、谁持有、谁在什么时机销毁？GC 凭什么不回收它
② 它该写在哪一层Actor / UObject / 组件 / 函数库：位置选错，代码就难以组织

是什么 · 版本差异

旧教程还能照抄吗

很多网上教程仍基于 UE4。直接照搬可能编译失败，也可能在新项目里沿用已经不推荐的结构。

主题UE4 写法UE5 写法
输入BindAxis / BindActionEnhanced Input
对象成员裸指针 + UPROPERTYTObjectPtr<>
全局服务Manager / GameInstanceUSubsystem 家族
坐标数值FVector 是 floatLWC · double
范本第一人称模板Lyra + Game Features
热更Hot ReloadLive Coding
编辑器VS + Visual AssistRider / VS Code
为什么会有这么多差异

UE4 是 2014 年的设计，UE5 在 2020 年后逐步替换。Epic 保留了向后兼容，所以旧代码还能编，但新项目不该照着写。

同类替换（认识名字即可）

StateTree 部分替代行为树 · MetaSounds 替代 Sound Cue · Chaos 替代 PhysX · World Partition 替代 Level Streaming

见到旧教程怎么办

先认版本：看发布日期、看有没有 Enhanced Input、看有没有 TObjectPtr。三样都没有，就是 4.x 的。

参考旧教程前，先确认它的引擎版本和输入系统。

课上一律按 5.8 讲，同时说明旧项目中仍会见到旧写法。学生需要能识别版本差异。判断版本时重点看发布日期、Enhanced Input 和 TObjectPtr。

运行崩溃访问空对象 / 数组越界 / GC 提前回收 → 断点 + 调用栈
用这四项帮助学生自测。很多报错并非语法问题，而是模块没加或头文件没包含。重点讲清编译错误、链接错误和运行崩溃的区别。
是什么 · 常见误区

它不是什么

× 误区一

不是「背完 C++ 语法」

语法书看完也写不出一行引擎代码。引擎要的是「知道写在哪」。

× 误区二

不是「以后只写 C++」

蓝图仍然是最好的表现层工具。真正的目标是「两个都会用」。

× 误区三

不是「记住几千个 API」

记不住很正常，找得到就行。编辑器补全比十年前好太多。

真实的门槛顺序（很多人搞反了）
以为的顺序学语法 → 背 API → 才能写代码 → 才能做项目
实际的顺序看懂一个功能 → 照着改 → 改了有效果 → 知道为什么 → 能自己设计
卡住的人停在「学语法」，因为看不到语法跟项目的联系
走通的人从「改一个数值」开始，先有反馈，再要原理

学习重点是理解代码的职责和位置，不需要先记住大量 API。

学生常问需要背多少 API。说明不需要以背诵为起点，可以先修改现有功能，观察结果，再回头理解原理。

为什么 · 蓝图边界

蓝图正在失去什么

文本代码和 AI 工具的发展，正在改变蓝图的使用范围。它在编辑器中的可视化优势仍然存在。

硬伤 01 · 版本管理二进制资产，合并不了

蓝图是 .uasset，本质是二进制。两个人改同一个蓝图，只能靠「你先提交我后改」，或者干脆分文件。代码能 merge、能 diff、能 review，蓝图不行。

硬伤 02 · 性能虚拟机解释执行

蓝图跑在 VM 上，逐节点解释。同一个逻辑，C++ 常常快一个数量级。热点逻辑放蓝图，是项目后期最常见的性能债。

硬伤 03 · AI 时代AI 写不动节点图

AI 工具通常更适合处理 C++、Python、Lua、C# 等文本。蓝图的二进制节点图难以直接参与文本生成、审查和重构流程。

蓝图目前最有价值的部分：编辑器生态
编辑器生态美术、TA、策划和音频成员可以直接在编辑器中修改和预览
材质、动画、Niagara、UMG 可视化预览，都是它的延伸
主要限制团队协作、性能分析和文本工具支持都不如代码方便
适用场景非程序成员可以直接修改逻辑、预览效果并参与迭代
蓝图在项目中的定位

版本控制、性能和 AI 工具支持，都在影响团队使用蓝图的方式。

对程序：蓝图从「主力」退成「胶水与调参层」
对非程序：蓝图仍是唯一入口，短期不会变
对你的选择：会蓝图不亏，但别把它当终点

根据团队分工和项目需求选择蓝图，同时保留使用 C++ 的能力。

介绍蓝图限制时避免简单化地否定它。按版本管理、性能和 AI 工具支持三个方面说明，再补充编辑器生态和非程序成员协作的优势。对程序员而言，蓝图通常承担连接逻辑和参数调整的工作；对非程序成员，它仍是重要的工作入口。

结论

这里重点讨论如何分层：根据职责选择 C++、脚本或蓝图，而不是只比较语言。

脚本适合承担的部分
版本控制：文本 diff / merge / review，团队协作不再靠喊
AI 协作：AI 能读、能改、能补测试，整条流水线跑得通
热更新：不进引擎也能改玩法，运营活动不用等版本
引入脚本的成本

调试体验差：断点、profiler、蓝图那种可视化都没有现成的
团队门槛：非程序成员需要学习语法，策划通常仍使用蓝图

  ACharacter

一个高频错误

在构造函数里 GetWorld() 或 FindPlayer——那时世界可能还不存在。这类问题表现为「偶尔崩」，最难查。

设计 Actor 时优先考虑组件组合，避免为了叠加能力不断增加继承层级。

呼应面向对象中的组合优先，避免把多种能力都堆进一个基类。生命周期部分重点提醒：构造函数里查询世界可能导致崩溃。

为什么要有 UBT：一条编译链

问题

引擎要支持 Windows / Mac / Linux / iOS / Android / 主机，每个平台的编译器、宏、链接方式都不同。

答案

自己造一套构建系统：用 C# 写描述，用一套工具链统管所有平台。这就是 UBT。

从按 F5 到编辑器起来，中间发生了什么
  [1] UBT（C#）          读 .Build.cs / .Target.cs，算出「要编哪些文件、用什么参数」
        │                只改 .cpp？走 Live Coding，跳过后面大半
        ▼
  [2] UHT（C++ 程序）     扫所有 *.generated.h，生成反射代码（.gen.cpp）
        │                这一步报错 = 反射标记写错
        ▼
  [3] 平台编译器         MSVC / Clang / 各主机 SDK，真正编译
        │                这一步报错 = 语法或头文件问题
        ▼
  [4] 链接器             把 .obj 和库连成 .dll / .exe
        │                这一步报错 = 缺模块依赖
        ▼
  [5] 起 Editor         加载模块，失败会弹「模块无法加载」
改 .cpp：Live Coding（Ctrl+Alt+F11）热补，几秒完事
改头文件 / 改 Build.cs：必须停编辑器整体重编译

这就是「我明明改对了为什么不生效」的第二种根因——第一种是根本没编译成功。

学生常遇到「代码改了却没有生效」的问题，可以沿这条编译链排查。每一段对应不同报错，讲清后才能定位问题。还要说明 Live Coding 能改什么、不能改什么。

依赖怎么连：三组属性

Build.cs 里的 ModuleRules，三组属性管三件事。

PUBLICPublicDependencyModuleNames

我这个模块对外暴露的头文件里用到的依赖。会传染给依赖我的模块

PRIVATEPrivateDependencyModuleNames

只在自己内部用，不对外暴露。不外传

DYNAMICDynamicallyLoadedModuleNames

运行时才加载，编译期不链接。用来做可选功能

常见依赖写法（照着抄就行）
  PublicDependencyModuleNames.AddRange(new string[] {
      "Core", "CoreUObject", "Engine", "InputCore" });

  // 用到 UMG 控件
  PrivateDependencyModuleNames.AddRange(new string[] { "UMG", "Slate", "SlateCore" });

  // 用到 AI 感知
  PrivateDependencyModuleNames.Add("AIModule");

  // 用到 Enhanced Input
  PublicDependencyModuleNames.Add("EnhancedInput");
口诀

public 会传染，private 不外传。只在自己 .cpp 里用 → private；出现在自己的 .h 里 → public。

真实报错：undefined symbol 十有八九是少加了一个模块名。这个错新手会被卡好几天
讲一个真实报错：改代码时突然一片红，链接时报 undefined symbol，八成是 Build.cs 少了模块名。判断规则一句话：出现在你自己的 .h 里 → public，只在 .cpp 里 → private。

头文件与包含：谁能看见谁

最容易混的一组概念。记住一句：IncludePath 是「能看见」，Dependency 是「能用」。

路径：决定 include 怎么写
PublicPublicIncludePaths；默认已含 Public
PrivatePrivateIncludePaths；默认已含 Private 与 Classes
影响改它们 = 改「别人 include 你的写法」，别乱动
只包含、不链接的特殊关系
PublicPublicIncludePathModuleNames
PrivatePrivateIncludePathModuleNames
含义能 include 头文件、能用里面的类型声明，但拿不到符号
用途头文件里只用到指针/引用，不需要真的链接
三种关系，一张图分清
  ┌─────────────────────────── 你的模块 ───────────────────────────┐
  │                                                                │
  │  #include "Other/Header.h"  ← 需要 IncludePath  「能看见」   │
  │         │                                                      │
  │         ├── 只用了 class FOther*（前向声明/指针）          │
  │         │     → 只需 IncludePath，不用 Dependency         │
  │         │                                                      │
  │         └── 调用了 FOther::DoSomething()                 │
  │               → 必须加 Dependency「能用」，否则链接不过   │
  └────────────────────────────────────────────────────────────────┘
判断方法：能 include 却链接不过，就是这组配错了。补 Dependency，别去改 IncludePath。
配合关系图解释，不逐条念定义。IncludePath 决定头文件搜索，Dependency 决定模块链接。能 include 但链接失败时，应检查 Dependency，而不是随意修改 IncludePath。

UHT 生成了什么

这些宏会为 UHT 提供类型信息，参与后续的代码生成。

// MyActor.h —— 你写的
#include "CoreMinimal.h"
#include "MyActor.generated.h"   // 必须是最后一个 include

UCLASS()
class MYGAME_API AMyActor : public AActor
{
    GENERATED_BODY()                    // 必须第一行
public:
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category="Stats")
    int32 Health = 100;

    UFUNCTION(BlueprintCallable)
    void TakeDamage(int32 Amount);
};
UHT 干了什么
读所有带 .generated.h 的头文件（不编译，只解析）
写MyActor.generated.h → 静态类型信息、属性偏移、宏展开
MyActor.gen.cpp→ RegisterCompiledInInfo、反射注册函数
符号作用
UCLASS()让类进入反射系统，蓝图可见、可派生
USTRUCT()让结构体可反射、可序列化、可在蓝图用
UENUM()枚举可在蓝图下拉框里出现
UPROPERTY()属性进反射 + 进 GC 分析（最关键）
UFUNCTION()函数可被蓝图调用 / 被委托绑定
UINTERFACE()接口可被蓝图实现
GENERATED_BODY()把生成的代码插进你的类
MYGAME_API 是什么

导出宏，来自模块名。漏写 = 链接不过，不是语法错误。这是新手最常见的「编译成功但链接失败」。

三条硬规则（违反就编不过）
1.generated.h 必须是最后一个 include
2GENERATED_BODY() 必须是类体第一行
3宏里的类型必须是反射可见的（UObject 指针 / 反射结构体 / 基础类型）
可以录屏展示 generated.h 的生成结果。三条硬规则能覆盖多数常见 UHT 错误。MYGAME_API 需要单独说明，它常表现为编译通过后链接失败。

GC · 谁能被回收

UObject 通常由引擎创建并由 GC 管理。需要正确保存引用，避免仍在使用的对象被回收。

引用链：从根出发可达的都活着
  Root Set（引擎自己抓着的：GEngine、GameInstance、Actor 等）
     │
     ├──→ 对象 A
     │       ├──→ 成员 X（标了 UPROPERTY）  ✓ 被扫描，活着
     │       └──→ 成员 Y（裸指针）          ✗ 不被扫描，可能被回收
     │
     └──→ 对象 B  ← 没有引用链到这里 → 回收

只有 UPROPERTY 标记的引用，才进 GC 分析。

非 UObject 结构体与 UObject 混用，要小心 FGCObject::AddReferencedObjects。

写法UE5 推荐
成员指针TObjectPtr<AActor> 而不是 AActor*（增量 GC 下才安全）
判空IsValid(Ptr) 而不是 Ptr != nullptr
弱引用TWeakObjectPtr<T> 不参与 GC 引用，用前判空
非 UObject用 TSharedPtr / TUniquePtr，它们不走 GC
手动标记AddToRoot() / RemoveFromRoot()，慎用
经典事故现场
  AActor* CachedTarget;          // 没标 UPROPERTY
  CachedTarget = GetTarget();
  // ... 几秒后 ...
  CachedTarget->DoSomething();      // 崩溃：对象已被回收

  UPROPERTY() TObjectPtr<AActor> CachedTarget;  // 正确

需要长期持有的 UObject 引用，应使用 UPROPERTY 等引擎支持的方式让 GC 识别。

常见问题是未标记 UPROPERTY 的对象成员后来变为空，因为 GC 没有识别这条引用。说明 IsValid 和 TObjectPtr 在 UE5 中的用法，并区分普通判空与对象有效性检查。

CDO 与 Package

两个绕不开的疑问：默认值从哪来？资产路径是什么？

CDO · Class Default Object
是什么每个 UClass 都有一个默认实例，在类注册时创建
在哪GetClass()->GetDefaultObject<AMyActor>()
作用蓝图里看到的默认值就是它；新对象以它为模板复制
所以改 C++ 默认值，蓝图里「没覆盖过」的项会跟着变
CDO 与实例的关系
  AMyActor::AMyActor()        →  创建 CDO（Health = 100）
        │
        ├── 关卡里放一个  →  复制 CDO  → 实例 A（Health = 100）
        └── 蓝图派生 BP_My  →  复制 CDO  → 改 Health = 250  →  实例 B（Health = 250）
Package · 资产的组织方式
是什么对象的容器，一个 .uasset 通常对应一个包
路径/Game/ThirdPerson/BP_Player.BP_Player（包名 + 对象名）
引用包可以互相引用，形成依赖图；加载一个可能带起一串
硬引用UPROPERTY() TObjectPtr<UTexture2D> Icon; → 加载父对象时一起加载
软引用TSoftObjectPtr<> / TSoftClassPtr<> → 用时才加载，推荐
为什么运行期别用 ConstructorHelpers

它只能在构造期用，而且强依赖路径字符串。运行期加载走 Asset Manager + 软引用，才可控。

两个疑问，两个答案
Q为什么我改了 C++ 默认值，新生成的对象就变了？
A因为新对象是复制 CDO，而 CDO 在类注册时用构造函数创建
Q为什么我加了一个贴图引用，加载就慢了一大截？
A因为硬引用把整条包依赖链都拉起来了，改成 TSoftObjectPtr
简要解释默认值来自哪里。软引用部分可以结合资源加载和包体大小说明，避免不必要的硬引用。

怎么学 · 学习闭环

学习闭环：四步转一圈

前面介绍知识结构，这里说明如何通过练习逐步掌握。

STEP 01模仿

照着别人的实现写一遍，形成手感。别问为什么，先让手会。

STEP 02动手

在最小场景里改一改，验证自己的理解对不对。这是唯一的验证方式。

STEP 03总结

把规律写成自己的话：什么情况用什么、为什么。写下来才算真懂。

STEP 04积累

变成资产：测试工程、函数库、笔记、图。下次直接用。

四步最容易断在哪
断在模仿只抄不改 → 换个需求还是不会
断在动手看完就算学会 → 三天后忘干净
断在总结做了很多但没有规律 → 每次都从零开始
断在积累做过的东西不留资产 → 三年后仍然只有经验没有工具
关键四步中「总结」和「积累」最容易被跳过，也最能减少重复工作
一圈的周期

一个小功能 = 一圈，几小时到几天。别指望一圈就进化一级，但也别做半圈就换方向。

怎么知道自己转了一圈

觉悟 · 边界

什么时候动引擎

关键词是「可维护」：改引擎的代价不在今天，在下次升级。

从「不动」到「动」的四级台阶，逐级往下走
  第 0 级  不改引擎：用现有 API / 组件 / 蓝图做出来
     │        代价：0        适用：90% 的需求
     ▼
  第 1 级  插件 / 子类 / 接口：扩展而不修改
     │        代价：低       适用：想要新行为
     ▼
  第 2 级  Editor Utility / 反射：绕开私有成员，别改可见性
     │        代价：中       适用：需要访问内部数据
     ▼
  第 3 级  直接改引擎源码：包在宏或注释标记里，方便 merge
               代价：高       适用：真的没别的路
为什么能不改就不改

下次升引擎版本时，你的改动要重放一遍。改得越深、越散，重放越疼。有人在 4.27 改的东西，到 5.0 花了三周才合回去。

真要改，怎么改

统一加一段标记注释（带项目名与日期），所有改动集中搜得到；能包在宏里就包在宏里；别改签名、只加接口。

改了 C++ 基类名，蓝图找不到父类 —— 用 CoreRedirects 修（Engine.ini 里配映射）
没有基类的蓝图可以 reparent，但先备份——reparent 不可逆
修改引擎的主要成本在版本升级和维护。若确实需要修改，要清楚标记并控制范围。按四个层级依次评估，多数需求可以在前两层解决。

借鉴源码时如何控制维护成本

除了让功能跑起来，还要考虑依赖、扩展方式和后续修改成本。

四条原则
能调就不拷能直接调用 API 就别复制实现——拷过来就等于接手维护
先看输入输出搞清它依赖什么、产出什么，再决定能不能借
找那个「旋钮」想在流程里插一脚，去找 Delegate、虚函数、可重载点
别跨层调Runtime 下别去调 Editor 代码，打不包
四种「借」的代价
方式代价什么时候用
直接调用最低接口正好够用
子类重写低想在某个点改行为
复制代码中只想抄思路，不想带依赖
改引擎源码最高真的没别的路
「找不到旋钮」时的排查顺序
1这个类有没有 virtual 函数可以重写？
2有没有 Delegate 可以绑定？（OnXxx 命名多半是）
3有没有 Component 可以替换，而不用改主体？
4有没有 接口 可以实现？
5有没有 Subsystem 可以扩展？
6都没有 → 才考虑改引擎，并按前面讲的方式标记
经验引擎的扩展点比你想的多得多。找不到，通常是没找全

借鉴代码后，要确认自己能够解释并维护它。

复制源码后即使能运行，也可能留下维护问题。评价标准包括能否理解依赖、找到扩展点并在后续修改。按五个排查顺序逐项检查。

为什么是这五件（每件对应一个坑）
01对应「只会用不改」 → 读懂自己项目的代码
02对应「不会挂组件」 → 掌握最基本的结构
03对应「照着旧教程写输入」 → 换上 5.x 的写法
04对应「遇到链接错误就懵」 → 亲手制造一次，以后不会怕
05对应「脑子里没有结构」 → 把隐性的理解画出来
