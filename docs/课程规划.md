## 这节课讲七块

### 1. 认识基本界面

先让人能在编辑器里找到东西、点得动、看得懂。

- 打开工程，分清视口、内容浏览器、大纲（Outliner）、细节（Details）
- 在关卡里点选、移动 Actor，看细节面板跟着变
- 玩一次：Play / PIE，停下来回到编辑
- 知道「现在改的是关卡里的这个东西」，先不展开蓝图和 C++

### 2. 游戏开发必备知识

只讲这局游戏真的会用到的几件，讲完立刻在编辑器里验证。

#### 2.1 2D 坐标系

- 2D 屏幕坐标：原点在左上角，X 向右、Y 向下，单位是像素；UMG / HUD 都用它
- 2D 数学坐标：原点可以任意放，X 向右、Y 向上；和屏幕的 Y 方向正好相反
- 两者都是平面，但 Y 轴朝向相反：写 UI 时不要拿数学课的直觉套屏幕坐标

#### 2.2 从 2D 到 3D

- 平面抬高就多出高度：2D 是两个轴，3D 是三个轴
- 屏幕坐标和世界坐标是两套东西，不能“加一个轴”直接混用
- UE 是左手系：X 向前、Y 向右、Z 向上，和数学课上常见的 Y 朝上不一样
- 位置、旋转、缩放分别对应 Location / Rotation / Scale
- Rotation 三个轴：Pitch 抬头低头、Yaw 左右转、Roll 侧翻；用手腕动作演示最直观
- 世界坐标和局部坐标的区别：Actor 自带的箭头是它的前方向，挂到父物体上之后会跟着转
- 单位是厘米：默认角色身高约 180，一格地板 100，建立尺度感
- 动手：在关卡里摆三个物体，分别沿 X / Y / Z 移动，再用旋转看清 Pitch / Yaw / Roll

#### 2.3 射线检测

- 一句话：从一个点朝一个方向发一条线，问「打到了什么」
- 两个输入（起点、方向）和一个输出（命中结果：打中了谁、打在哪、离多远、法线朝哪）
- 线检测（Line Trace）和球形检测（Sphere Trace）的区别：一个点扫、一个有粗细
- 通道（Trace Channel）先只讲 Visibility 和 Camera，知道「只测该测的东西」
- 碰撞预设只带一句：Block / Overlap / Ignore，知道射线会被什么挡住
- 在这局游戏里的用途：准星打靶、拾取、判断脚下有没有地面，挑一个作为演示
- 动手：鼠标点哪打哪，打印出命中的 Actor 名字和距离

#### 2.4 游戏循环与 Tick

- 一帧的流水线：输入 → 游戏逻辑（蓝图/C++/Tick/AI/计时器）→ 物理与动画 → 提交渲染 → 显示，然后下一帧
- 游戏线程和渲染线程是两条线：Tick 阻塞会拖整帧；渲染线程不跑游戏逻辑
- 帧预算：60 fps = 16.7 ms，30 fps = 33.3 ms，120 fps = 8.3 ms；先分清掉帧和卡顿（Hitch）
- 用 `stat unit` 看 Game / Draw / GPU 谁接近预算，再决定优化哪边
- Tick 是「每帧都跑」，输入回调和碰撞是「发生了才跑」；先分清这两类
- Tick 能关就关：`bCanEverTick`、Tick Interval、事件、计时器、委托
- DeltaTime：这一帧花了多久。乘上它，速度才是每秒多少，而不是每帧多少
- 帧率高低不该改变游戏速度；用 DeltaTime 做一次「每秒移动 200」的验证
- 动手：让物体每帧前进，分别用「每帧固定距离」和「乘 DeltaTime」，对比不同帧率下的结果

### 3. 先建立面向对象思维

不背概念，用这局里的角色把两个词讲清楚：类是图纸，对象是造出来的东西。

- 类与对象：类型是图纸，关卡里放进去的是对象；一个类可以有很多对象
- 每个对象有自己的数据：改 A 的血量，B 不变
- 继承 is-a：玩家是一种 Character，敌人也是一种 Character；共同身份往上提
- 组合 has-a：Actor 是容器，组件是挂在身上的一块能力；优先组合，别造超大类
- 组件能复用、能拆：同一个能力可以挂给不同对象
- 讲法：先问“敌人和玩家共同点是什么”，再问“这个能力一定要靠继承吗”
- 这一节只建立思维，不写代码；名字和箭头看懂即可

### 4. C++ 语法速成

目标只有一个：能读懂类声明，不要求现场手写。

- 蓝图和 C++ 是同一个类的两种写法，不是两套系统
- 一个类两个文件：`.h` 写声明（这个类有什么），`.cpp` 写实现（具体怎么做）
- `GENERATED_BODY()` 必须放在类体最前面，删了编译就报错
- 前缀：`A` Actor、`U` UObject / 组件、`F` 结构体、`E` 枚举、`I` 接口
- 指针理解成遥控器：指着一个对象，不是对象本身
- 指针与 GC：UObject 由引擎管生命周期；成员指针加 `UPROPERTY` 才算持有
- `TObjectPtr` 是 UE5 推荐写法，本质仍是指针
- 创建对象：组件用 `CreateDefaultSubobject`，运行时对象用 `NewObject`；不要 `delete`
- 四个入口：构造函数（默认值/组件）→ BeginPlay（初始化/绑定）→ Tick（持续变化）→ EndPlay（解绑/清理）
- 编译链路：UHT 生成代码 → 编译 → Live Coding 热更或重启编辑器；改头文件通常要重新编译
- 学生不会 C++：不要求写，只要求指认；语法能省就省

#### 零基础只认这几个锚点

- 头文件看「这个类有什么」，cpp 看「具体怎么做」
- 只认三样：类名、`UPROPERTY` 变量、`UFUNCTION` 函数
- 函数体先找构造函数 / `BeginPlay` / `Tick` / `EndPlay`，知道它什么时候跑
- 课上只改数值和一行日志，不写新函数
- 读代码先追一条链路：输入 → 逻辑 → 表现，不在无关文件里打转

### 5. UEC++：让引擎认识你的类型

C++ 语法讲完，再讲 UE 自己的标记。顺序不能反：先有类，才谈得上给类加宏。

#### 5.1 类型宏

- `UCLASS()`：UObject 派生类；蓝图能不能继承看 `Blueprintable`
- `USTRUCT()`：纯数据类型，值传递，不走 GC，必须有 `GENERATED_BODY()`
- `UENUM()`：枚举；蓝图可用必须写成 `: uint8`，再加 `BlueprintType`
- `UMETA(DisplayName="…")`：给枚举项起显示名，编辑器里看到的是它
- `UINTERFACE()`：只是给 UHT 的反射壳，真正的方法写在 `I` 前缀的实现类里
- 这些宏都交给 Unreal Header Tool 生成反射、序列化和蓝图支持
- `QINGCHANG_API` 是模块导出宏，换工程时跟着换

#### 5.2 成员宏

- `UPROPERTY()`：变量进反射 / GC / 编辑器
- `UFUNCTION()`：函数暴露给蓝图，也是动态委托能绑定的前提
- `UDELEGATE()` / `DECLARE_DYNAMIC_MULTICAST_DELEGATE…`：事件签名
- 常用标记：`EditAnywhere` / `VisibleAnywhere`、`BlueprintReadOnly` / `BlueprintReadWrite`、`BlueprintCallable` / `BlueprintPure`、`Category`
- 一句话记：`UPROPERTY` 管看见，`UFUNCTION` 管调用，`UDELEGATE` 管通知

#### 5.3 委托

- 发生方只管 `Broadcast`，关心方自己绑定；双方不需要互相认识
- 单播一个回调，多播一对多；带 `Dynamic` 的才能进蓝图
- C++ 绑定动态委托用 `AddDynamic`，普通 C++ 委托才用 `AddUObject` / `BindUObject`
- 对象离开时 `RemoveDynamic`，通常在 `EndPlay` 里做
- 先绑后广播：广播时没人听，这次的值就丢了

#### 5.4 接口

- 解决“都有同一个能力，但没有共同父类”
- `U` 接口是反射壳，`I` 接口写方法；实现方多继承 `I`
- `BlueprintNativeEvent`：C++ 给默认实现，蓝图可覆写，生成 `_Implementation`
- `BlueprintImplementableEvent`：只有声明，实现在蓝图里
- 调用统一走 `Execute_`；`Cast` 要求具体类，接口只要求能力

### 6. Gameplay 框架

前面都是零件，这一节讲它们怎么装成一局游戏。七页，细讲。

- 四层职责：GameInstance / World（全局）→ GameMode / GameState（一局）→ PlayerController / AIController / PlayerState（玩家）→ Pawn / Character / Components（身体）
- 继承树只认三条线：UObject → Actor → Pawn → Character；Actor → Controller → PlayerController / AIController；Actor → Info → GameModeBase / GameStateBase / PlayerState
- 生成顺序：GameMode 是关卡里第一个 Actor，创建 GameState / PlayerState；玩家加入时创建 PlayerController，RestartPlayer 生成 Pawn 并占有
- 谁拥有谁：Controller possess Pawn；HUD / Camera 跟 PlayerController；GameState 和 PlayerState 负责复制给客户端
- 规则、状态、玩家数据分开：GameMode 只存服务器规则，GameState 存这一局所有人可见的状态，PlayerState 存跟人走的数据
- 每个类只回答一个问题：谁定规则、这一局现在怎样、谁在操作、谁的身体、跨关卡要留什么
- 组件是“一块可复用的能力”，挂在 Actor 上；只讲职责，不在课件里点名具体实现组件
- 讲完要能在这局游戏里对上号：PlayerState 和 AIController 先知道完整框架里放哪，本课用简化实现

#### 我的代码什么时候跑

- InitGame / InitGameState：一局开始，GameMode 先搭台，早于普通 Actor 的 BeginPlay
- PostLogin / RestartPlayer：玩家加入，创建 Controller，生成并占有 Pawn
- BeginPlay：这个对象进入游戏时跑一次，做初始化
- Tick：每帧跑，适合持续变化的东西；能在事件里做就不要放 Tick
- 输入回调：玩家按键时才跑，不按就没有
- EndPlay / Logout：对象或玩家离开时跑一次，做收尾
- 一句话记住：先规则，后身体；先进场，再 Tick；离开时收尾

### 7. 课件之后：现场演示 AI 开发（单独一场）

课件只讲界面、循环、语法和框架；具体开发演示放在课件之后，单独一场。目标是让观众看到：从基础工程到一局能玩的小游戏，AI 怎么参与，老师怎么审查。

演示用的基础工程预置到什么程度：

- 工程、关卡、光照、刷怪点、PlayerStart
- 角色移动、相机、Enhanced Input（开火键已绑，`Fire()` 里只有一行日志）
- Idle / Run / Jump / Fall 动画状态机
- HUD 布局摆好，读数还没绑定
- 规则、状态、敌人、HUD 的类和骨架都在，方法留空

演示脚本（按现场进度取舍）：

1. 数值与广播：改一个数，广播出去，HUD 跟着变
2. 点射：准星 → 射线 → ApplyDamage
3. 敌人：追人、攻击、死亡
4. 胜负与 HUD：刷怪、计数、结算、重开

#### 演示怎么走

1. 先看现状，再写需求：哪个类、哪个方法还空着；目标、改哪个文件、不许动什么、验收标准。提示词现场分析、现场写，口语化没关系
2. 生成后先看 diff：改了哪些文件，有没有越界
3. 编译，运行，按验收标准试一遍
4. 通过就提交；不通过把报错原样喂回去
5. 老师只讲两件事：这个决定为什么放在这一层（架构判断），哪里不能信 AI

#### 必须人工审查的点

- 射线有没有忽略自己、通道对不对
- 伤害是不是走 `ApplyDamage`
- 委托有没有重复绑定、死亡会不会触发两次
- Tick 里有没有不必要的开销
- AI 编造的 API：编译不过就是它，正好讲怎么读报错

#### 改完代码为什么不生效

- 改 C++ 要编译；Live Coding 能热更一部分改动，改类结构、加成员变量往往要重启编辑器
- 遇到「代码明明改了却没反应」，先确认编译过没有，再确认跑的是不是最新模块
- 演示：故意改一行打印，走一遍「改 → 编译 → 看到输出」的完整链路
